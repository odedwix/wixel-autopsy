Learn what's wrong

Every failure, down to its root cause

A failed run has a red edge and its first error on the card. Hover the error icon for every failing step. A run that made nothing says why, in plain words, with the agent's own last message.

🧾Why a run made nothing

Checked in this order, so each run gets the most specific reason:

1
Still working
2
Not enough credits: e.g. "Needs 88 · has 30 · over the 30/day plan limit". The agent checks the price and stops, usually without an out-of-funds event.
3
Stopped by the user
4
Failed: with the failing step and message
5
Waiting for the user: a question or widget (a video plan, a brief) never answered
6
Never finished
7
Continued in another skill, or handed back to the main chat (sub-agents)
8
Ended without making anything: the agent's last words, in any language
On Oct 6–7, 81% of wixel-ads-lite's empty runs stopped at the credit wall, two-thirds of them over the free plan's daily limit. In wixel-ads, most waited on a plan the user never approved.

🧯The root cause, not the wrapper

The gateway wraps most provider errors as INVALID_ARGUMENT. Autopsy follows the failure chain to the bottom, e.g. MiniMax H3 Max does not accept settings, even for a generation that only left a job id.

🙁Mood and feedback

Sentiment per turn (neutral, positive, confused, frustrated), thumbs up/down and their tags, and the worst mood across turns on every card. Insights compare frustration with and without tool errors.

🏷️Errors in context

Every failing step shows its arguments, its output and what the agent did next. In Insights, the failure that costs the most output is shown next to the runs it didn't hit.

Learn when time is wasted

Where a run's time goes

One bar, from the first message to the end of the last counted turn. Every moment counts once: two videos generating at the same time are one stretch of video time. Waiting on the user and failed calls get their own colour, so it's obvious when a run is slow because of us and when because of them.

Try it: pick a skill, hover the bar (illustrative split)

 

👻Hidden timeouts

Several tools (generateMusic, BuildPresentation, Generate*Async…) report success after ~15 minutes while the job is still running. Autopsy counts them as errors: 12 of 65 generateMusic calls on Oct 6–7 waited the full 15 minutes and came back with no file.

⏳Time lost, one stated rule

Each failed call's own time, plus one recovery per run of consecutive failures: from the first failure until the next successful attempt of that operation started (else the turn's end). Measured, not guessed.

🔁Polling and repeats

Fleet's Efficiency tab measures the time spent between status polls (stories-creation: 16 h a week) and identical calls repeated after they already succeeded (video-logo-animation repeats the same read ~7k times a week).

📐How long should the agent wait? model estimate

For every operation Fleet looks at the measured durations and finds the cap τ that minimizes the expected time to a success: E(τ) = E[min(T, τ)] ÷ P(T ≤ τ). Cap too short and good jobs get killed; too long and stuck jobs waste minutes. It never goes below 1.5× the p95 of successes, and it's labelled as an estimate because it assumes a restart is free (it costs credits).

Insights

The skill as a whole, in plain words

The Insights tab (I) is computed in your browser from the runs in view, so it follows the skill, window, filters and search, and costs nothing extra upstream. It leads with findings, each with its evidence and a click to the runs behind it.

💡What the numbers say

  • How often a run that tried made the output.
  • Who the runs that never tried are: sub-agents, the credit limit, one-message sessions.
  • The model that takes the most time, and the one that costs the most.
  • The failure that costs the most output: runs it hit vs the rest.
  • Frustration with vs without tool errors.
  • Runs that went 3+ messages with nothing made and no error (in a review of 18 such chats, about 7 in 10 were the request itself: beyond the skill, missing material, content policy).
  • Time to result, and whether a newer skill version does better or worse.

💸Models: time and cost illustrative

Every generation model by its price-list name, with time per call and cost per call. Costs come from the product's own list price per Genix graph; failed calls count as free.

Then the funnel, top errors, mood and quotes, what users asked for, and "All the numbers": every tool, repeated requests, runs per day, skill versions (printed in full in the PDF).

🔬Fixes only when proven

A change is suggested only when the cause is proven: a missing file traced in the codex; an image host that fails ≥5× the Wix-hosted rate across every call; a made-up tool name the codex itself writes. Everything else says "No proven fix" and what would prove one.

🧰Fix per skill

For each skill an issue happens in: what its failing calls show, the change to its instructions, the exact lines and files (GitHub links), examples, and a Copy prompt for Claude Code limited to that skill's files, with a redacted failing call and an eval case.

📝Fix briefs

On demand for a whole issue: up to 3 example sessions, the Genix root cause, the codex files to look at, a suggested fix, how to verify it (rate per codex version, eval sets) and a redacted repro. Copy as Markdown, email it, or draft the fix with Claude (read-only, as a diff).

🚨What changed

Flags a day whose failure rate, tokens, frustration, kept outputs and more moved beyond the 7 days before it, and names the codex version that took over that day: the alert after a deploy.

🤝Shared decisions

Issue statuses (accepted, fixed in version…, won't fix, duplicate, with a note) and pinned skills are shared with everyone using the same Fleet folder.

📚Knowledge in the repo

The day rollups and a readable digest (knowledge/README.md: numbers, what we learned, top issues and proven fixes, wait times, patterns, efficiency) are committed, so the findings outlive anyone's laptop.

The logic

How Autopsy decides what counts

Most sessions mix skills: 30–40% of a skill's session turns are usually other skills' work, like a logo made after an ad. Counting whole sessions would blame (or credit) the wrong skill. So a session counts for a skill turn by turn.

Try it: one session, seven turns

Viewing skill: wixel-ads

1 · The turn that loads the skill claims the session

Turns before it never count. A skill loads when the agent calls the skill tool, or (since Sep 30) when the platform preloads it into the first message. Both count.

2 · Later turns stay until another family takes over

A skill's family is its helpers, learned from how often skills load together (partners in ≥3% of its turns, their sub-steps, and shared utilities). The Counting button shows each helper and why; you can edit it or switch to whole sessions.

3 · Outputs are what the session itself made

Its own writes, write steps, metering events and hand-overs during the counted turns, plus assets server-side jobs built. Not whatever else is in a shared project: campaign siblings' posts used to be credited by mistake.

4 · What the skill makes is learned

Its main output type plus any type a quarter of its producing runs make. A wixel-ads run that only made an image counts as "tried, no video" and says "made image instead".

🛡️ Gentle on production

Every upstream call has a concurrency cap and spacing, shown live in the status bar. On-screen work goes first; background work waits. Timeouts and full queues make it back off. Switching view cancels queued queries.

🎲 Busy days are sampled

Above ~400 sessions a day a deterministic sample is taken (sessions whose id starts with certain characters). The status bar shows the share.

⚡ Fast, then fresh

Cached days show instantly and refresh in the background. Refresh (R) only fetches sessions newer than what's on screen: 20–40 s whatever the window.

🏢The shared copy: built once a day, read by everyone

Run on a laptop, every copy queries Trino itself; ten people means ten times the load. The shared copy works from a daily build: one producer queries Trino once each morning (every skill with ≥10 sessions in 30 days, up to yesterday), and the server only reads the result, so any number of people can use it at once without touching Trino. It's on its way to the back office as a Wix Serverless app behind staff sign-in.

Good to know

Privacy, limits and common questions

Who can see this data?

Autopsy shows what the Wixel admin page shows, including end users' emails and prompts, so it's for Wix staff only. A local copy listens on your machine only; a hosted copy must sit behind back-office sign-in. Shared links, summaries and Fleet's committed knowledge never include end-user emails, and example errors have emails, phone numbers and URL query strings stripped.

Does it slow down production?

It reads the analytics cluster (Trino), not production serving, with strict caps per system. The admin API and Temporal are called only for what you open, and cached. Fleet costs about a minute of Trino per day, once. The shared daily build means readers never query Trino at all.

How fresh is the data?

Locally: live, with Refresh adding new sessions in 20–40 s. The shared copy: up to yesterday (UTC), rebuilt every morning. Fleet: a day is final 6 hours after it ends; today refreshes at most every 30 minutes.

What can't it see?

Rendering, export and player failures on the client, output quality itself, and anything that never reaches the agent's entries or events. Fleet's Data tab lists these so nobody over-reads the numbers.

Are the "time lost" numbers real?

Yes: counts, durations, recoveries, tokens, versions and outcomes are measured from the agent's own entries. Time lost uses one stated rule. Savings and recommended waits are estimates and are labelled as such, with how they were computed.

Why does a skill's number differ from the admin page?

Because Autopsy counts only the turns that belong to the skill and its helpers, and only the outputs the session itself made. Switch Counting to "whole sessions" to compare.

Can it change anything?

No. It's read-only everywhere. Even "Draft the fix with Claude" runs with read-only tools and returns a diff for a person to apply.

Who do I ask?

The repo is odedwix/wixel-autopsy; its README covers every feature and data source in detail.
